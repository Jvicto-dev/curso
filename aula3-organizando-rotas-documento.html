01Por que separar as rotas

Até a aula 2, todas as rotas moravam no server.ts. Com o CRUD de users completo, ele já passava de 70 linhas, misturando a configuração do servidor, a conexão com o banco e a regra de cada rota.

Cada assunto novo (products, orders, login...) deixaria esse arquivo ainda maior. A regra que passamos a seguir é simples:

  • Um arquivo por assunto: tudo de users fica em users.routes.ts, tudo de products em products.routes.ts.
  • O server.ts só liga e registra: ele não sabe mais nada sobre usuários.

Assim fica fácil achar onde mexer, e uma mudança em users não corre o risco de quebrar products.

02O arquivo de rotas é um plugin

No Fastify, um plugin é uma função que recebe o app e acrescenta coisas nele, no nosso caso rotas. As rotas de users vão pra src/routes/users.routes.ts:

▤ src/routes/users.routes.ts
import type { FastifyInstance } from "fastify"
import { randomUUID } from "node:crypto"
import { connection } from "../config/database.js"

export async function usersRoutes(app: FastifyInstance) {
    app.get("/", async () => {
        const users = await connection("users").select("*")
        return users
    })

    app.post("/", async (request, reply) => {
        const { name, email, password } = request.body as UserBody
        const user = { id: randomUUID(), name, email, password }
        await connection("users").insert(user)
        return reply.status(201).send(user)
    })

    // GET, PUT e DELETE em "/:id" seguem o mesmo molde
}

O que cada peça faz:

  • export async function usersRoutes: é o plugin. Precisa do export pra ser importado no server.ts. É async porque o Fastify espera o plugin terminar de montar as rotas antes de ligar o servidor.
  • app: FastifyInstance: o tipo do app. Aqui ele chega como parâmetro, e sem o tipo o TypeScript não sabe que ele tem .get, .post etc.
  • "/" e "/:id": os caminhos ficam sem o /users. Quem coloca o /users é o server.ts.
  • Os imports mudam de caminho: de dentro de src/routes, o banco fica em "../config/database.js" (o ../ sai da pasta routes).
IMPORTANTE

A função não roda sozinha: ela só é chamada quando o server.ts faz o register.

03O server.ts enxuto

Depois da limpeza, o server.ts cabe em 11 linhas: cria o app, registra as rotas e liga o servidor.

▤ src/server.ts
import fastify from "fastify"
import { env } from "./shared/env/environments.js"
import { usersRoutes } from "./routes/users.routes.js"

const app = fastify()

app.register(usersRoutes, { prefix: "/users" })

app.listen({ port: env.PORT }).then(() => {
    console.log("Rodando na porta: " + env.PORT)
})
  • app.register(usersRoutes): chama a função do plugin passando o app pra ela. É isso que faz as rotas do arquivo passarem a existir no servidor.
  • { prefix: "/users" }: o começo do caminho de todas as rotas daquele arquivo.
NA LIMPEZA

Apague os imports que ficaram sem uso (connection e randomUUID; o VS Code mostra eles meio apagados). Aproveite também pra trocar o process.env.PORT do console.log por env.PORT, que já foi validado pelo Zod.

CUIDADO

Escrever app.get("/users") dentro do arquivo vira /users/users, porque o prefixo já foi colocado. Aí GET /users dá 404.

Vantagem extra: o /users fica escrito num lugar só. Se um dia a rota virar /clientes, muda só o prefix no server.ts.

05Repetindo o molde: products

Assunto novo = arquivo novo + uma linha no server.ts. Sempre assim.

  1. Crie o arquivo na pasta routes.
  2. Exporte uma função que recebe o app.
  3. Acrescente uma linha de register no server.ts.
▤ src/routes/products.routes.ts
import type { FastifyInstance } from "fastify"

export async function productsRoutes(app: FastifyInstance) {
    app.get("/", async () => {
        return [{ name: "Teclado" }]
    })
}
▤ src/server.ts · acrescenta
import { productsRoutes } from "./routes/products.routes.js"

app.register(usersRoutes, { prefix: "/users" })
app.register(productsRoutes, { prefix: "/products" })

Ainda não existe a tabela products, por isso a rota devolve uma lista fixa. A migration pode ser criada depois com npm run knex -- migrate:make create_products.

06Testando: nada mudou por fora

Isso tem nome: refatoração, que é mudar a estrutura do código sem mudar o comportamento. Quem usa a API não percebe nada; quem mantém o código agradece.

Pra provar que nada quebrou, rode npm run dev e dispare os pedidos do requests.http:

▤ requests.http
GET {{baseUrl}}/users
POST {{baseUrl}}/users
GET {{baseUrl}}/products
  • /users: responde igual a antes. Rode o POST e depois o GET pra ver o usuário salvo no banco.
  • /products: a rota nova, que devolve a lista fixa.

07Erros comuns

404

Todas as rotas do arquivo dão 404.

Faltou o app.register no server.ts. → Registre o plugin com o prefix.

404

/users dá 404, mas /users/users funciona.

O caminho foi repetido dentro do arquivo. → Use "/" e "/:id" no arquivo de rotas.

módulo

Cannot find module '.../config/database.js'

Faltou o .js no import ou o ../ pra sair da pasta routes. → Confira: "../config/database.js".

export

does not provide an export named ...

Faltou o export antes da função, ou o nome está diferente no import. → Confira o nome nos dois arquivos.

tipo

TypeScript reclamando do app.

Faltou o tipo no parâmetro. → Escreva app: FastifyInstance.

POR QUE .js SE O ARQUIVO É .ts?

O projeto usa "type": "module" no package.json, e nos imports em ESM o TypeScript resolve o .js para o arquivo .ts.

Se o servidor nem sobe, olhe o terminal do npm run dev: a primeira linha vermelha diz o arquivo e a linha do erro.
