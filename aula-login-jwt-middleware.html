O PROBLEMA

O HTTP não tem memória

Cada requisição chega sozinha. O servidor não lembra quem fez a requisição anterior.
SEM CRACHÁMandar email e senha em toda requisição. Chato e perigoso: a senha fica viajando o tempo todo.
COM CRACHÁManda email e senha uma vez, recebe um token e mostra o token nas próximas.
PENSA ASSIMShow com pulseira: na entrada você mostra o ingresso e o documento uma vez e ganha uma pulseira. Daí pra frente, o segurança só olha a pulseira.

OBJETIVO

Criar a necessidade do token antes de mostrar código: o HTTP é "stateless", cada requisição é independente.

CONDUZA ASSIM

  • Use a analogia da pulseira a aula toda: login = mostrar o ingresso, token = pulseira, middleware = segurança na porta.
  • Não precisa usar a palavra "stateless" se a turma estranhar; "o servidor não lembra" basta.

UM AVISO SOBRE O NOME

Hash não é criptografia

CRIPTOGRAFIAUma tranca com chave: quem tem a chave abre e lê o original. Tem ida e volta.
HASHUm moedor de carne: o bife vira carne moída e nunca mais volta a ser bife. Só tem ida.
Pra senha a gente usa hash: nem a própria API sabe a senha original.
NO DIA A DIAMuita gente fala "criptografar a senha". O nome certo é gerar o hash da senha.

OBJETIVO

Desfazer a confusão de nomes antes de explicar como o bcrypt funciona.

CONDUZA ASSIM

  • Pergunte: "a API precisa saber a senha original de alguém?" Não: no login ela só precisa saber se a senha digitada é a mesma. Pra isso, comparar hashes basta.
  • Por que não criptografar? Porque a chave teria que ficar guardada na API. Se o banco e a chave vazarem juntos, todas as senhas aparecem. Com hash não existe chave pra vazar.
  • Vocês vão ouvir "senha criptografada" o tempo todo, inclusive de gente experiente. Tudo bem entender o que a pessoa quis dizer, mas no código e na prova o nome é hash.

O PROBLEMA DO HASH SIMPLES

Mesma senha, mesmo hash

▤ tabela usuario · com um hash simples (SHA-256) ana · "123456" ──▶ 8d969eef6ecad3c29a3a629280e686cf... bruno · "123456" ──▶ 8d969eef6ecad3c29a3a629280e686cf...
▸
Quem vê o banco descobre que a ana e o bruno usam a mesma senha.
▸
Pior: existem listas prontas com o hash das senhas mais comuns. Achou 8d969eef...? É 123456.
▸
E o SHA-256 é rápido demais: um computador testa bilhões de senhas por segundo.

OBJETIVO

Mostrar os dois problemas que o bcrypt resolve: hashes iguais pra senhas iguais, e velocidade.

CONDUZA ASSIM

  • Esse hash é real: é o SHA-256 de "123456". Pesquise "8d969eef6ecad3c29a3a629280e686cf" no Google e a senha aparece. Isso é uma "rainbow table" na prática.
  • O hash em si não tem defeito: o problema é que todo mundo que usa "123456" ganha exatamente o mesmo resultado.
  • Guarde os dois problemas: o próximo slide resolve o primeiro (salt) e o seguinte resolve o segundo (custo).

A SOLUÇÃO 1

O sal: um tempero aleatório

Antes de gerar o hash, o bcrypt sorteia um salt: um texto aleatório, diferente pra cada senha.
▤ a ideia hash( senha + salt )
▤ bcrypt.hash("9999", 8) rodado duas vezes $2b$08$aspHpIT8qMnxYUDkCRQ48uZ69gtIdTOuZkV1LHteALMTv9IKcLO3m $2b$08$KcRRY1.5e2IWBI54FrPH9ONXgWB6GGZsC1znxRq2PcB0bKHbSSDBW
Mesma senha, hashes diferentes. As listas prontas não servem mais.

OBJETIVO

Mostrar o salt resolvendo o problema do slide anterior.

CONDUZA ASSIM

  • Esses dois hashes são reais: a mesma senha "9999", gerada duas vezes. A parte em verde-água é o salt sorteado; a parte em verde é o hash.
  • Faça ao vivo: crie dois usuários com a mesma senha no POST /usuario e mostre no GET que o senha_hash dos dois é diferente.
  • O salt não é secreto: ele fica guardado junto, dentro do próprio senha_hash. Ele não serve pra esconder nada, serve pra deixar cada hash único.
  • Analogia: duas pessoas fazem o mesmo bolo (a senha), mas cada uma joga um tempero sorteado diferente. Os bolos saem com gosto diferente.

A SOLUÇÃO 2

O que tem dentro do senha_hash

▤ um senha_hash de verdade $2b$08$aspHpIT8qMnxYUDkCRQ48uZ69gtIdTOuZkV1LHteALMTv9IKcLO3m
$2b$
a versão do algoritmo: bcrypt
08
o custo: 2⁸ = 256 voltas no moedor
salt

Pra API, 17 ms num login não é nada. Pra quem tenta milhões de senhas, vira uma eternidade.

OBJETIVO

Ler o senha_hash pedaço por pedaço e explicar o número 8 do bcrypt.hash(password, 8).

CONDUZA ASSIM

  • Os tempos foram medidos de verdade com o bcryptjs, no computador onde a aula foi preparada (no de vocês pode variar um pouco). Cada +1 no custo dobra o tempo.
  • Isso resolve o segundo problema do SHA-256 (rápido demais): o bcrypt é lento de propósito, e dá pra deixar mais lento conforme os computadores ficam mais rápidos.
  • Em produção se usa 10 a 12. Usamos 8 na aula pra ficar rápido.
  • Repare que tudo que o bcrypt precisa pra conferir a senha depois (versão, custo e salt) está dentro desse texto. É o assunto do próximo slide.

POR DENTRO DO JWT · 1

Por que o jwt.io lê o token?

▤ a parte do meio do token (payload) eyJzdWIiOiJiZTM0NzU1MSIsInBlcmZpbCI6ImFydGlzdGEiLCJpYXQiOjE3NjQwMDAwMDAsImV4cCI6MTc2NDA4NjQwMH0 ▼ decode (base64) {"sub":"be347551","perfil":"artista","iat":1764000000,"exp":1764086400}
▸
base64 é só outro jeito de escrever o mesmo texto, com letras que viajam bem na internet.
▸

OBJETIVO

Responder a pergunta que sempre aparece: "se dá pra ler no jwt.io, cadê a segurança?". A segurança do JWT não está em esconder, está em não deixar alterar (próximos slides).

CONDUZA ASSIM

  • Demonstração sem site nenhum: no console do navegador (F12), rode atob("eyJzdWIi...") com a parte do meio do token. O JSON aparece. (Com esse token funciona; alguns tokens têm - ou _ e aí o atob reclama, porque o JWT usa uma variação do base64.)
  • Faça o mesmo com o header (a primeira parte): aparece {"alg":"HS256","typ":"JWT"}.
  • iat e exp são datas em segundos desde 1970 (timestamp). Dá pra converter em sites como epochconverter.com.
  • Ligue com o slide do hash: hash não volta, base64 volta pra qualquer um. São coisas bem diferentes.

Como a assinatura nasce

▤ a receita (HS256) assinatura = HMAC-SHA256( header + "." + payload , JWT_SECRET )

É um hash que mistura o conteúdo com a secret. Muda uma letra de qualquer um dos dois e a assinatura sai totalmente diferente.

OBJETIVO

Mostrar que a terceira parte do token não é mágica: é um hash do conteúdo misturado com a secret.

CONDUZA ASSIM

  • Esses valores são reais: com a secret "segredo", essa é exatamente a assinatura do token do slide "O que é um JWT?".
  • É o mesmo "HS256" que aparece no header: HMAC com SHA-256. É ele que o reply.jwtSign usa por baixo.
  • Ligue com a aula de senha: lá o salt deixava cada hash único; aqui a secret deixa a assinatura impossível de fabricar sem ela.
  • Sem a secret, dá pra ler o token (é só base64), mas não dá pra gerar uma assinatura que bata.

POR DENTRO DO JWT · 3

O que o jwtVerify faz

1
Separa as três partes do token pelo ponto
2
Recalcula a assinatura com o header + payload que chegaram e a sua secret
3
Compara com a assinatura que veio no token: diferente = 401
4
Confere o exp: já passou da validade = 401
O JWT.IO FAZ O MESMOQuando você cola a secret no site, ele recalcula a assinatura com ela e diz se bate. É o passo 2 e 3, feito no navegador.

OBJETIVO

Explicar o que acontece dentro do request.jwtVerify(), que até aqui era uma caixa-preta.

CONDUZA ASSIM

  • Repare que a API não guarda os tokens que criou. Ela não precisa: com a secret, ela consegue conferir qualquer token na hora. Por isso o JWT é chamado de "stateless".
  • Consequência: não dá pra "cancelar" um token antes do exp só com isso. Por isso o expiresIn não deve ser longo demais.
  • Se trocar o JWT_SECRET no .env, todos os tokens antigos param de valer: a assinatura recalculada não bate mais com nenhum.

QUANDO DÁ ERRADO

Erros que vão aparecer

env
Invalid environment variables: faltou o JWT_SECRET no .env.
plugin
jwtSign / jwtVerify is not a function: faltou o app.register(jwt) no server.ts.
401
Login sempre falha: o usuário foi criado antes do hash. Crie um novo.
401
/me sempre falha: esqueceu o Bearer (com espaço) antes do token, ou o token expirou.
cors
Testador mostra "Sem resposta" e o console diz blocked by CORS policy: faltou o app.register(cors), ou a lista de methods.

OBJETIVO

Antecipar os erros mais comuns da aula, pra turma reconhecer a mensagem.

CONDUZA ASSIM

  • Depois de mudar o .env, reinicie o npm run dev: o tsx watch não recarrega o .env sozinho.
  • Se trocar o JWT_SECRET, todos os tokens antigos param de valer (a assinatura não bate mais). Faça login de novo.
